# idm-kit

Internet Download Manager 6.43 build 15 的试用期上限离线补丁。纯 Python 实现，
带图形界面，可打包成独立 exe。

只针对下面这一个精确版本做过验证，其他 build 一律拒绝执行。

> **只想装上能用？** 请直接看 **[使用说明.md](使用说明.md)**。那份文档面向普通使用者，只有操作步骤、现象判断和出问题时的处理办法，不含任何原理说明。
>
> 本文档面向需要了解实现细节的读者。

## 快速开始

```powershell
# 图形界面（推荐）
python main.py

# 命令行：输出诊断报告
python main.py --check

# 命令行：打补丁 / 还原 / 导出报告
python main.py --patch
python main.py --restore
python main.py --export

# 命令行：结束 IDM 进程（提权后使用，界面会自己调它）
python main.py --stop
```

**推荐以管理员身份运行**。原因是实测发现：**普通权限下进程表可能是残缺的** —— 同一台 360 进程的机器上，普通权限运行的打包版只枚举到 23 个进程，于是 `taskkill /IM IDMan.exe` 会回报「没找到」而 IDM 其实正在运行。管理员权限下进程表完整，进程枚举和 `taskkill` 全部按原样工作。

标题栏显示当前模式（`IDM 工具（管理员）` / `IDM 工具（普通权限）`），用户一眼可辨。

普通权限下也不是不能用，但判据必须设对。**判断 IDM 是否在运行以进程枚举为准**：`runtime.idm_running()` 找不到 `IDMan` 时，要先看进程表读得是否完整（`total_process_count()`），残缺就返回「无法确认」而不是「没运行」。写文件同样**能不提权就不提权**：先试着以 `r+b` 打开目标文件，能写就直接改，不能写才弹一次 UAC。

### 不要把 1001 端口当作 IDM 在运行的证据

早期版本曾用「端口优先」判断，这是错的，实测推翻了它：

```
TCP    127.0.0.1:1001    LISTENING    4      ← pid 4 = 内核
```

1001 的占用者是 **`IDMWFP` 驱动**，不是 `IDMan.exe`。驱动是常驻服务，只要它加载着端口就一直监听——**哪怕 IDM 根本没启动**。于是会出现「端口说有、进程枚举说没有」的矛盾，而两个都是对的：驱动在，IDM 不在。

现在端口的用途只剩一个：说明**驱动已加载、具备接管能力**。IDM 启动后才会真正接管浏览器下载，所以 `_check_channel` 在「端口在监听但进程表里没有 IDMan」时会给出 `[注意]` 而不是 `[正常]`。

运行时不需要任何第三方库，只用 Python 标准库。

## 程序结构

```
idmkit/
├── constants.py    全部与构建版本绑定的常量（地址、锚点、哈希、注册表项）
├── pe.py           PE 定位原语：Anchor 定位、字节比对、地址换算
├── patch.py        补丁状态机：识别 / 应用 / 还原，含回读校验
├── runtime.py      运行时探针：进程、完整性级别、注册表、端口、驱动、扩展
├── diagnose.py     诊断引擎：把探测结果翻译成「事实 / 含义 / 建议」三段式
├── reporter.py     导出诊断包（文本 + JSON + 环境 + 扩展 + 日志）
└── ui.py           tkinter 界面
```

分层原则：`pe.py` 只认字节，`patch.py` 只认状态，`runtime.py` 只认现象，
`diagnose.py` 只负责把现象翻译成人能读的结论。界面不包含任何判断逻辑，
它只渲染 `diagnose` 的输出。

### 安装路径不写死

`Program Files` 归 `BUILTIN\Administrators` 所有，`BUILTIN\Users` 只有
`ReadAndExecute`，所以改那里的 `IDMan.exe` 必须提权。但这不是唯一的部署方式：
IDM 的安装器是 NSIS，支持 `/D=`，用户可以装到非系统盘。

因此定位安装目录时**注册表优先，硬编码路径只作最后后备**：

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | `HKCU\Software\DownloadManager\ExePath` | IDM 自己写的，指向它实际运行的 exe |
| 2 | 卸载信息的 `UninstallString` | 安装程序写的，去掉文件名即目录 |
| 3 | 硬编码的 `Program Files` 两个候选 | 注册表都读不到时的猜测 |

卸载信息里的 `InstallLocation` **实测是空值**，不可依赖。

实测验证过：把 `ExePath` 临时指向用户目录后，`find_idm_dir()` 跟着走；
把它指向不存在的路径或删除后，回退到 `UninstallString`，仍能正确定位。

配套的行为是**能不提权就不提权**：`ui._is_writable()` 直接试着以 `r+b` 打开
目标文件——ACL 继承、只读属性、占用状态都会影响结果，实际试一次比读 ACL 可靠。
能写就当场改完，不能写才走提权分支。


## 补丁原理

试用期上限是全局变量 `[0x77bd28]`。判定逻辑在 `0x46753c`：

```asm
0x467539  mov  ecx, [ebp-0x24]     ; 已用天数（IDM 内部维护的计数器，不落注册表）
0x46753c  cmp  ecx, [0x77bd28]     ; 与上限比较
0x467542  jae  0x4675c2            ; 已用 >= 上限 -> 过期分支
```

上限本身由 `0x44cf37` 处的代码块按注册状态算出 30 或 15：

```asm
A1 24 BD 77 00   mov  eax, [0x77bd24]
F7 D8            neg  eax
1B C0            sbb  eax, eax
83 E0 0F         and  eax, 0xf
83 C0 0F         add  eax, 0xf        ; -> 30 或 15
A3 28 BD 77 00   mov  [0x77bd28], eax
```

把上限改成一个不可达的大数，所有下游判定一并失效。

## 补丁内容

| 补丁 | 文件偏移 | 定位锚点 | 原始 | 补丁后 |
|---|---|---|---|---|
| A：上限计算 | `0x4C340`（6 字节） | `0x4C337`（整块 20 字节，只改 `[9..14]`） | `83 E0 0F 83 C0 0F` | `B8 <imm32> 90` |
| B：`.data` 默认值 | `0x379528`（4 字节） | `0x37952C`（目标**之后** 8 字节，目标 = 锚点 − 4） | `1E 00 00 00`（30） | `<imm32>`（默认 99999999） |

两处地址都由锚点搜索得到，脚本里没有写死任何一个文件偏移。

**补丁 A 为什么只改中间 6 字节。** 原 20 字节块里含两条带绝对地址的指令：

```asm
A1 24BD7700   mov eax,[0x77bd24]   -> disp32 位于 RVA 0x4CF38
A3 28BD7700   mov [0x77bd28],eax   -> disp32 位于 RVA 0x4CF47
```

它们在 PE `.reloc` 表里各占一项。如果整块替换，第一个 disp32 会相对重定位项平移一个字节，加载器把映像基址差值加错位置，直接写坏新指令的地址字段（实测内存中出现 `28 BD 77 00` → `28 76 78 00`），补丁会打开一个非法写入地址。所以这两条指令**字节保持原样**，只替换等长的中间算术。

**补丁 B 为什么是必须的。** `[0x77bd28]` 在镜像 `.data` 里的默认值本来就是 30，无论 `0x44cf37` 那段代码路径是否执行，这个值在进程启动时就已经存在。只打 A 会让"代码算出的值"和"数据段初值"不一致。

**锚点的选择有一条硬规则：锚点字节区间不得覆盖被本补丁修改的字节。** 否则补丁一落地锚点就消失，脚本再也回不到现场。补丁 B 最初把目标 dword 本身（`1E 00 00 00`）包含进锚点，打补丁后锚点永久失效；改用目标之后的 8 字节（`38 93 69 00 D0 03 6A 00`，两个链接基址指针 `0x699338` / `0x6A03D0`）后，锚点在原始与已补丁文件中各出现恰好 1 次。

## 诊断引擎

诊断的设计目标只有一个：**让读到报告的人立刻知道哪里坏了、为什么、该怎么办。**

IDM 6.43 不写错误日志（`%APPDATA%\IDM\GlobalErrors.log` 不存在），所以不存在
"打包一个现成日志"的选项，只能靠主动采集环境状态。但单纯堆数据没有意义——
一份列了四十一项注册表值的报告，仍然回答不了"为什么浏览器不接管下载"。

因此每项检查都输出三段：

| 段 | 作用 | 例子 |
|---|---|---|
| **事实** | 观测到的原始状态，不带判断 | `正在运行，pid 388，权限 普通用户` |
| **含义** | 这个状态代表什么 | `以普通用户权限运行` |
| **建议** | 需要做什么（仅异常时才给） | `不要以管理员身份启动 IDM` |

最后再给一个**单一结论**，由优先级顺序裁决，而不是把判断留给读者：

```
安装 → 版本 → 补丁状态 → 无操作说明 → 运行权限 → 驱动 → 通道 → 扩展 → 备份
```

比如"IDM 报 Cannot launch IDM"这个现象，报告会直接落到 `IDM 权限过高`
这一条并给出修法，而不是让用户自己在十一条检查里找线索。

检查项共 11 条：安装、程序版本、激活状态、试用上限、自动更新、IDM 进程、
运行权限、浏览器通道、网络驱动、浏览器扩展、原始备份。

### 自动更新预警

这是报告里对用户最有价值的一条。IDM 每两周检查一次更新（二进制里的原文是
`IDM checks for a new release every 2 weeks`），而更新会把 `IDMan.exe` 换回
官方版本，激活随之失效。

`runtime.update_schedule()` 从注册表 `LastCheckQU`（Unix 时间戳，秒）反推：

- 距上次检查过了多少天
- 按两周周期推算，还有多久会再检查

于是工具能**提前**说"大约 14 天后会再检查一次"，而不是等失效之后才让人来排查。

> 顺带纠正一个早先的错误结论：原先以为已用天数存在注册表 `Therad` 值里。
> 实测该值**不存在**，IDM 6.43 的注册表里没有任何名为 `Therad` 的项。

### 导出内容

`reporter.export()` 在桌面生成 `idm-diag-<时间戳>.zip`：

| 文件 | 内容 |
|---|---|
| `01-诊断结论.txt` | 人读的报告，开头三行就是结论 / 原因 / 建议 |
| `02-诊断结论.json` | 同上的结构化版本 |
| `03-浏览器扩展状态.txt` | 三个浏览器引擎的扩展安装情况 + 注册表注册项 |
| `04-安装目录文件.txt` | 安装目录的完整文件清单与大小 |
| `05-IDM安装日志.txt` | `IDMSetup2.log` 尾部 80 行 |
| `06-使用说明.txt` | 给拿到报告的人的阅读指引 |

## 状态检查

| `state` | 含义 |
|---|---|
| `PATCHED (trial limit = N days)` | 两个站点都已改写且天数一致，附上实际天数 |
| `PATCHED but INCONSISTENT` | 两个站点天数不一致，通常意味着文件被手工改过 |
| `PRISTINE (untouched official build)` | 哈希与官方原始版本一致，尚未打补丁 |
| `UNKNOWN (...)` | 站点读不到或互相矛盾 |

**状态由站点内容决定，不由文件哈希决定。** 已补丁文件的 SHA256 随 `--days` 取值变化，用固定哈希做主判据会把所有非默认值误报成未知构建。哈希只用于确认"这是未改动的官方版本"这一种情况。

站点 B 的判定顺序有一条容易搞错的地方：**先判"是否与站点 A 一致"，再判"是否等于 30"**。因为 `--days 30` 会重写站点 A 的代码，却改不动 `.data` 里本来就是 30 的那个 dword。若先判字面值 30，`--days 30` 会被误判成未打补丁。

## 自动更新：后果与恢复

### 事实基础

IDM 会定期自动检查更新，这个行为写死在程序里。二进制中的原文：

```
IDM checks for a new release every 2 weeks by requesting an update page from its home site.
Check for &Update
```

Quick Update 的产物是**替换 `IDMan.exe` 本身**，所以它一旦跑起来，补丁就被抹掉了。

**这件事没有注册表开关可以关。** 结论是确定的，排查过程如下。

二进制里唯一像开关的值名是 `CheckUpdtVM`。反汇编它的唯一引用点（`0x45A4CC`）：

```asm
0x0045A499  mov  ax,  word ptr [0x698900]   ; 数据区内容 31 30 00 = "10"
0x0045A49F  mov  cl,  byte ptr [0x698902]
0x0045A4A5  mov  word ptr [esp], ax
0x0045A4AC  mov  byte ptr [esp+2], cl       ; 在栈上拼出字符串 "10"
0x0045A4CC  push 0x6a2550                   ; "CheckUpdtVM"
0x0045A4D2  call dword ptr [0x695090]
```

它把字符串 `"10"` **写进去**，而不是读出来做真假判断——这是一个**状态标记**，不是布尔开关。所以在脚本里实现"改注册表关闭自动更新"不具备可行性；写一个语义未经证实的值进去，只会伪造出一种"已经关掉了"的假象。

### 不关会怎样

| 情况 | 后果 |
|---|---|
| 被同 build 覆盖 | 补丁失效，退回 30 天试用态。程序、下载数据、注册表配置均不受损 |
| 更新到更新的 build | 同上，且工具会**拒绝执行**（SHA256 不在白名单）。这是设计意图：绝不往未知二进制里写字节 |

两种情况都不会损坏程序，也不会丢已完成的任务。

### 怎么恢复

先在界面上看结论，或执行 `python main.py --check`。

**情况 A：结论是「等待激活」**（被同版本覆盖）

打开工具，点「激活」；或者：

```powershell
python main.py --patch
```

几秒完成。锚点重新搜索，不依赖任何写死的偏移。

**情况 B：结论是「不认识这个版本」**（更新到了新版本）

此时工具会主动拒绝写入，需要退回已知版本：

1. 卸载当前 IDM（控制面板，或安装目录的 `Uninstall.exe`）
2. 用官方安装包 `idman643build15.exe` 重新安装（安装包 SHA256 见[适用范围](#适用范围)）
3. 打开工具，点「激活」

仓库本身不保存安装包（见 [.gitignore](.gitignore)），需要自行留存。

### 预防

按可靠性排序：

1. 定期打开工具看一眼结论。这是最可靠的一道保险——无论 IDM 以什么方式更新，补丁状态一测便知，恢复只需点一下。
2. 装完 IDM 后把界面选项里所有带"检查更新"字样的勾取消（见 `使用说明.md` 第四节）。这是常规做法，不依赖任何未验证的注册表值。
3. 把 `IDMan.exe` 设为只读，让更新写入失败。**可行性未经验证**，可能干扰 IDM 自身行为，故未实现。


## 浏览器集成：扩展报 Cannot launch IDM

### 症状

装好 IDM、打完补丁、IDM 自己下载完全正常，但浏览器里的 IDM 扩展失效。Chrome 与 Firefox 同时报出同一句话：

```
Internet Download Manager extension for Chrome/Firefox has been installed.
Error: Cannot launch IDM, either IDM application is not installed, or some of its files are corrupted
```

**这句话是误报**——IDM 装得好好的。

### 机制

扩展的连接逻辑（`background.js`）是先连本机端口，失败才回落到 native messaging：

```javascript
La = ["127.0.0.1:1001", "0.1.0.1:1001"]
...
if (a < La.length) {
    a = this.S = new WebSocket(`ws://${La[a]}/?cid=…&rnd=…`,
                               "plugin.v3.internetdownloadmanager.com");
} else {
    a = this.S = browser.runtime.connectNative("com.tonec.idm");   // 兜底
}
```

IDM 6.42+ 的集成主通道是本机 1001 端口上的 WebSocket，native messaging 只是备胎。所以 Chrome 和 Firefox 会一起挂——它们连的是同一个端点。

该端点由 IDM 的网络过滤驱动（`IDMWFP` / `idmwfp.sys`）监听，并且做 **Origin 白名单校验**。实测（同一台机器、逐一改变量）：

```
Origin: chrome-extension://ngpampappnmepgilojfohadhhmbhlaek  ->  HTTP/1.1 101 Switching Protocols
Origin: http://127.0.0.1:8812                                ->  连接被重置
不带 Origin                                                  ->  连接被重置
带 permessage-deflate / Sec-Fetch-*                          ->  不影响结果
```

**唯一决定成败的是 Origin。** 只有扩展身份能连上，用普通网页或脚本去探测 1001 一律被拒——所以不要拿一个自建网页当作"扩展失效"的证据，那种测试从设计上就不可能通过。

### 真正的原因：IDM 不能以管理员身份运行

如果 IDM 是**以管理员权限**启动的，浏览器（中等完整性级别）会因 Windows 的 UIPI 规则无法与它建立这条通道，1001 直接重置连接。

对照实测：

| IDM 进程权限 | 从正确 Origin 发起连接的结果 |
|---|---|
| 管理员（High IL） | 连接被重置 |
| 普通用户（Medium IL） | `HTTP/1.1 101 Switching Protocols` |

安装目录里那个 `MediumILStart.exe`（内部名 `MediumIL`，Tonec 签名）是 IDM
自己用来做这件事的辅助模块。但它不是通用的降权启动器：实测把某个 exe 的路径
当参数传进去，它直接以退出码 0 结束，什么都不启动，所以不能拿来复用。

> **打补丁的动作本身是提权运行的**：它停掉又重启 IDM 时，IDM 会继承管理员
> 令牌，从而触发这个问题。工具已经接管了这一步，见下面小节。

### 工具自己怎么做

本工具推荐以管理员身份运行，而子进程默认继承调用者的令牌 —— 直接 `Popen`
会把 IDM 一起拉成 High 完整性级别，等于自己制造这个问题。所以「启动 IDM」
一律走 `runtime.launch_idm()`：

| 工具自身权限 | 做法 | 结果 |
|---|---|---|
| 普通权限 | 直接 `Popen(IDMan.exe)` | 子进程本来就是 Medium |
| 管理员 | `explorer.exe <IDMan.exe>` 代跑 | explorer 以登录用户身份常驻，由它启动的进程回到普通权限 |

降权有没有成功**由回读决定**，不靠假设。启动后轮询读回 `IDMan` 的完整性
级别：是 Medium 就报告「浏览器可以连接它」；仍然是 High 就明确说「请双击桌面
图标启动」—— 那条路径不走本工具，一定是普通权限。shell 会不会照做不属于我们
的契约，所以只回读，不推断。

如果工具发现 IDM **已经**以管理员权限跑着，点「启动 IDM」不会再去拉第二个
进程，而是问你要不要关掉它、再以普通权限重启（关闭那一步需要一次管理员授权）。

### 修法

1. 点「启动 IDM」，按提示走。
2. 或者手动：右击 IDM 快捷方式 → 属性 → 兼容性，确认**没有**勾选"以管理员身份运行"；不要从管理员权限的终端里启动 `IDMan.exe`；关掉 IDM 后从开始菜单正常打开。

IDM 自己开机自启（`HKCU\Software\DownloadManager\LaunchOnStart = 1`）走的是普通用户权限，那条路径是正常的。

### 怎么确认修好了

做一次真实的浏览器下载，看 IDM 是否接管。判定依据是**服务端是否收到多个并发 Range 请求**——那是 IDM 多线程分段下载的指纹，浏览器自身下载是顺序单流：

```
[xx] /dl  Range=bytes=233600-8388607     <- 线程 1
[xx] /dl  Range=bytes=233600-            <- 线程 1 续传
[xx] /dl  Range=bytes=4316943-           <- 线程 2，从不同偏移开始
```

或者直接查 IDM 主窗口的下载列表，以及文件是否完整落盘。

## 设计说明

### 地址层次：为什么换机器也有效

看到 `0x77bd28` 这类地址，容易误以为补丁依赖运行时地址、换机器就会失效。实际要分三层看：

| 层次 | 例子 | 是否固定 | 本方案是否依赖 |
|---|---|---|---|
| 文件偏移 | `0x4C340`、`0x379528` | 同一 build 固定 | 是（落笔位置），但由锚点搜索得出，脚本未写死 |
| RVA | `0x37BD28` | 同一 build 固定 | 是（配合运行时基址） |
| 运行时 VA | `0x77BD28`、`0x134BD28` | ASLR 每次都变 | 否 |

补丁改的是**磁盘文件里的字节**，发生在加载之前，此时 ASLR 还没介入。`0x77bd28` 只是链接基址（`0x400000`）下的 VA，它出现在指令的操作数字段里（文件字节 `28 BD 77 00`），加载时由 `.reloc` 表修正。脚本从不写这个地址，只在锚点里匹配这些字节。

- 补丁 A 的两条绝对寻址指令（`A1 24 BD 77 00` / `A3 28 BD 77 00`）**字节保持原样**，所以 `.reloc` 条目依然对得上；只替换中间的 6 字节算术。
- 补丁 B 改的 `.data` 初值是 `int` 而非指针，本身没有重定位条目。
- 早期版本用 `days-left.ps1` 读内存时，用的是 `模块运行时基址 + 0x37BD28`，这是 ASLR 正确的写法。该脚本已移除（见[文件清单](#文件清单)）。

**换机器的前提**：同一个 `IDMan.exe`（SHA256 `E3FC655A…BBFD8`）。同一个安装包装出来的文件字节完全相同，所以锚点匹配、补丁结果也完全相同。SHA256 allowlist 把住这一关，不同 build 会在写盘之前 abort。

实测：整个文件里两个锚点在原始与已补丁文件中各只出现 1 次；pristine → patched 的输出哈希确定为 `AC81B418…E8D58`；多次重启 IDM，运行时基址在 `0x3A0000` / `0xC80000` / `0xF90000` / `0xFF0000` / `0xFD0000` / `0x250000` 之间变化，读数始终是 `99999999`。

### 失败策略

所有检查都发生在写入之前，任何一项不通过，文件保持原样：

- SHA256 不在白名单 → 拒绝执行（`--force` 可跳过）
- 锚点命中数 ≠ 1 → 拒绝执行
- 原字节与预期不符 → 拒绝执行
- IDM 进程仍在运行 → 拒绝执行
- 目标文件不可写 → 拒绝执行

### 幂等性

重复执行是安全的。工具不依赖文件哈希判断"是否已打补丁"（哈希会随 `--days` 变化），而是用补丁 A 中**打补丁后依然存在的 9 字节前缀**定位站点，再看紧随其后的 6 字节：若是 `B8 <imm32> 90` 就说明已经改过，直接报告当前天数并退出。

## 打包

```powershell
python build.py              # onedir（推荐）
python build.py --onefile    # 单文件
python build.py --console    # 保留控制台，便于看报错
```

**默认产出 onedir 形态**，不是单文件。这个选择有实测依据：

单文件（`--onefile`）每次运行都要把自身解压到 `%TEMP%`。在受限令牌或 ACL 被
干预的环境下，引导程序会直接失败：

```
[PYI-xxxxx:ERROR] Could not create temporary directory!
```

隔离测试的结果（同一个 exe，只换 `--runtime-tmpdir`）：

| 解压目录 | 结果 |
|---|---|
| `C:\Users\...\Desktop\...`（workspace 内） | 成功 |
| `C:\Users\...\Documents\...` | 失败 |
| `C:\Users\...\AppData\Local\Temp` | 失败 |
| `%TEMP%` 下的子目录 | 失败 |

提权运行（High 完整性）则成功，说明不是程序缺陷。**onedir 形态不需要临时目录，
从根上避开了这一类环境差异**，因此作为默认选项。

代价是产物体积（约 27 MB，1026 个文件）且必须整个文件夹一起分发。

## 已知限制

- **补丁后 Authenticode 签名变为 `HashMismatch`。** Windows 加载器不靠证书有效性决定是否运行，程序照跑；Defender 实测未拦截。
- **补丁后哈希不是固定的。** `AC81B418…E8D58` 只对应默认的 `--days 99999999`。用其他天数时产物哈希不同，本文档中所有"补丁后哈希"的引用都只适用于默认参数；判断状态请用工具，不要比对哈希。
- **还原依赖 `.bak`。** 备份只在首次打补丁时生成，删掉它就无法回滚，只能重装。
- **补丁不涉及注册流程**，不需要屏蔽服务器域名。但是否存在服务端校验属于另一回事，本方案不做任何保证。
- **注册表里没有"已用天数"这一项。** 早先的文档称它在 `HKCU\Software\DownloadManager\Therad`，实测该值**不存在**。IDM 6.43 把可用的时间信息记在 `LastCheckQU`（检查更新的 Unix 时间戳）与 `LstCheck`（可读日期），工具据此推算自动更新的时间线（见[诊断引擎](#诊断引擎)）。因此报告只陈述"试用上限"，不声称能算出剩余天数。
- 早先的文档提到注册表里有一个"冗余备份键" `HKCU\Software\Classes\CLSID\{84797876-C678-1780-A556-0CD06786780F}`。**实测该键并不存在**，相关常量已从 `constants.py` 移除。同一批结论里 `InstallLocation` 也是空值 —— 涉及 IDM 注册表布局的说法都已按实测重写。
